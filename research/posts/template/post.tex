\title{Patching the Import Address Table}
\subtitle{This post is oriented towards Windows applications.}

\section{Background}

Recently, I've been exploring an issue whose solution involves redirecting calls targeting one function towards another - something that isn't difficult by any
			stretch of the imagination. Techniques like \href{https://malwaretech.com/2015/01/inline-hooking-for-programmers-part-1.html}{trampoline hooking} (or
			'\href{https://www.microsoft.com/en-us/research/project/detours/}{detours}' as Microsoft calls them),
			\href{https://mark.rxmsolutions.com/hook-via-vectored-exception-handling/}{vectored exception handling},
			\href{https://dimitrifourny.github.io/2014/07/02/vtable-hooking.html}{virtual table hooking}, using a hypervisor/breakpoints,
			or even just overwriting the import address table (IAT), export address table (EAT) are all viable and the majority of them would get the job done, and there
			are hundreds of open-source implementations of each technique available for reference. So why not use one of them?

There are two key issues here; firstly, the solution has no way of cleanly executing in the context of the affected process
			(this could be achieved by spawning a thread in the process via \href{https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-createremotethreadex}{CreateRemoteThreadEx},
			but that requires permissions the solution application may be unable to gain at runtime, and-) secondly, the implementation needs to have minimal performance
			impact on the process, to the extent that the replaced call should execute \textit{faster} than the original and take no more time to setup.
			This means that writing to process memory at runtime isn't viable due to time constraints, therefore it was decided that some form of persistent binary modification needs to take place.
			\\

			With the decision to patch the binary itself having been made, I figured that patching the import address table would be the easiest way to have a portable solution
			across Windows applications, and with any luck, the principles (abstracting away from the file format itself) could be applied to Linux and macOS in the future.

So, how can we patch the IAT of a binary to the effect that it loads a separate dynamic-link library (DLL) every time the binary is run?
			\\

			I started looking online for writeups about IAT patching, but was overwhelmed by the number of posts that cover IAT hooking at runtime, as opposed to persistent
			overwiting of the table in a target file's binary. The closest I came to finding resources on the matter included hasherezade's \href{https://hasherezade.github.io/IAT_patcher/}{IAT Patching utility} (which, despite not being suited towards my goal, is an interesting tool that you should try) and
			\href{https://www.wired.com/images_blogs/threatlevel/2011/02/Symantec-Stuxnet-Update-Feb-2011.pdf}{Stuxnet's technique for patching the IAT of a DLL}.
			While both of these are genuinely useful resources, they actually have in-depth documentation about the process of IAT patching - hence this post.
			\\

			Note: For the purpose of this post, I will be using 'IAT patching' to refer to the persistent binary modification technique, and 'IAT hooking' to address the runtime modification of the table or thunks, even though they are generally interchangable and IAT patching is considered a technique for IAT hooking.
